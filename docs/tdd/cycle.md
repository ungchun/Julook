# TDD Cycle

## 정의

한 사이클은 **red → green → refactor → green** 4단계.

통상 30초 ~ 5분 안에 한 바퀴. 10분을 넘기면 사이클이 너무 크다는 신호이므로 쪼갠다.

## 단계별 규칙

### 1. RED — 실패 테스트 추가

- 프로덕션 코드 건드리기 **전**에 테스트를 쓴다.
- 전체 테스트를 돌려 **새 테스트가 실제로 실패**하는지 확인.
- 처음부터 통과하면 잘못된 테스트다. 다시 쓴다.

**왜**: 실패를 눈으로 보지 않은 테스트는 "이 테스트가 실제로 무언가 잡는다"는 근거가 없다.

### 2. GREEN — 최소 코드로 통과

- 테스트를 통과시키는 **최소한**의 코드만 쓴다. 일반화는 Phase 3에서.
- 새 테스트만이 아니라 **전체 테스트**를 돌린다.
- 모두 통과 시 종료.

**왜**: 전체를 돌려야 이번 변경의 부작용(회귀)을 놓치지 않는다.

### 3. REFACTOR — 주변 설계 개선

- 방금 바꾼 코드와 그 **주변**의 가독성, 중복, 이름, 경계를 손본다.
- 기능 변경 금지. 테스트 추가/삭제 금지. 구조만 바꾼다.
- 각 리팩토링 단위를 작게 유지 (한 번에 한 가지).

**왜**: 버그는 대개 설계 문제의 "증상". 버그 주변을 함께 다듬으면 근본 원인이 옅어진다.

### 4. GREEN — 리팩토링 재검증

- 전체 테스트를 다시 돌려 리팩토링으로 아무것도 깨지지 않았음을 확인.
- 실패 시 즉시 리팩토링을 되돌리고, 사이클을 더 작게 쪼개 다시 시작.

**왜**: 리팩토링은 "의도적으로 기능을 안 바꾸는 변경". 테스트가 그 의도를 증명한다.

## 작업 유형별 적용 방식

| 작업 | 사이클 |
|------|-------|
| 새 기능 | 4단계 모두 |
| 버그 수정 | red → (green 생략) → refactor → (green 생략). 재현 테스트 먼저, 증상 제거 후 근본 설계 정리 |
| 리팩토링 | 커버리지 확보 → refactor → green. 테스트가 부족하면 먼저 characterization test 추가 |

## 사이클이 적용되지 않는 것

- 문서 수정 (단, 코드 예시가 실제 코드와 맞는지 확인)
- 리소스 (이미지, Localizable.strings)
- 설정 파일 (`.xcconfig`, `Info.plist`) — 단, 설정이 동작을 바꾸면 통합 테스트 필요
