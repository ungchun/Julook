# 테스트 교차 검증

**같은 세션에서 쓴 테스트는 믿지 않는다.** 최소 2~3번 새 세션을 열어 검증한다.

## 왜 교차 검증인가

- 같은 세션의 모델은 조금 전 자기가 짠 프로덕션 코드에 맞춰 테스트를 **무의식적으로 맞춘다** (확증 편향).
- 잘못된 테스트는 잘못된 코드를 "통과"시킨다. TDD의 기반이 무너진다.
- 새 세션의 모델은 테스트만 보고 의도를 재추론하므로 누락된 엣지 케이스를 발견할 가능성이 높다.

## 절차

1. TDD 사이클로 기능 완성.
2. **새 세션**을 연다. 앞 세션의 맥락을 공유하지 않는다.
3. 새 세션에게 다음 프롬프트로 검증 요청:

   > "다음 테스트 파일을 읽고, 이 테스트들이 검증하려는 의도를 모두 나열해라. 그다음 누락된 경계 사례가 있다면 지적해라. 프로덕션 코드는 먼저 읽지 마라."

4. 지적 사항이 있으면 새 실패 테스트로 추가 → Phase 1부터 다시.
5. 최소 **2회** 반복. 큰 변경이면 **3회**.

## 새 세션이 동의하면

- 테스트 네이밍이 의도를 정확히 드러낸다는 신호.
- 그래도 "남은 위험 있는지 30초만 더 고민"해 본다.

## 새 세션이 반대하면

- 반대 내용을 그대로 기록.
- 원 세션으로 돌아가서 반박/수용 판단.
- 수용 시 Phase 1 (실패 테스트)부터 다시.

## 미래 확장

- 슬래시 커맨드 `/verify-tests {테스트 파일}` 로 이 절차 자동화.
- 이 문서의 `검증:` 필드가 실제로 교차 검증된 테스트를 가리키도록 연결.
